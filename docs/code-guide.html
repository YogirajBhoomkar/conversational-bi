Conversational BI: the complete code guide

You type a business question in plain English. The app asks a data tool called Genie, writes a short answer, draws a chart and shows the table and SQL behind it. This one page explains how the whole app works, assuming you have never used Mastra, React or OAuth before.

Last verified against the files on disk on 2026-11-02. The project had no git repository at that time, so there is no commit id. Where this guide and the code disagree, trust the code.

How to read this

Everyone: read sections 1 and 2, then 28 (one question, start to finish).

New developers: add sections 3 to 5, run the app (section 4), then read sections 6 to 27 in order, and 33 before you change anything.

People who ship or run it: sections 30 to 33 and 35.

The code is TypeScript (JavaScript with types). You do not need to know it deeply. Each snippet has a plain explanation under it, and snippets are shortened from the real files.

1. The big picture

The app is a chat for business questions about reinsurance placements and reinsurer capacity. There are two programs:

  • The server (folder server/), built with a framework called Mastra. It holds the "brains": AI agents, the connection to Databricks, and login.
  • The UI (folder ui/), built with React. It is the chat page you see in the browser.

In production one server process serves both the API and the built UI (port 1976 with npm start). In development the UI runs on port 5173 and passes requests through to the server on port 4111.

What happens when you ask a question

1

You type "Chart FOT premium by region" in the browser and press Send.

2

The UI sends it to the server at /bi/chat.

3

The server hands the question to the supervisor agent, an AI (Claude by default) with instructions like "you coordinate specialists".

4

The supervisor delegates to a Genie agent, one per data area. That agent calls Databricks Genie, which writes SQL, runs it and returns rows. For a chart request, Genie returns the chart data as one cell of JSON.

5

Plain code, not an AI, turns that JSON into a real table and a chart description.

6

The supervisor writes a short answer. While this happens, the server streams live progress ("Running the query...") to the browser.

7

The server sends one final package: the answer, the table, the chart description and the SQL. A moment later it may send follow-up question ideas. The UI draws everything.

 Browser (React UI)             Server (Mastra)                              Databricks
 ------------------             ----------------                             ----------
  chat box --POST /bi/chat-->  supervisor agent (Claude)
                                   |-- delegates --> Genie agent --tool--> Genie  (writes + runs SQL)
                                   |                       |
                                   |                       +-- chart JSON --> chartSpec.ts (plain code)
  progress,  <--live stream--   writes the short answer
  answer, chart,                 collector box carries rows, SQL, chart past the AI
  table, SQL
Key idea

The AI never makes up numbers. All figures come from Genie's real query results. The AI only decides who to ask and explains the result. Tables and charts are built by plain code from the real rows.

4. Run it on your machine

What you need

  • Node.js. The README says version 20 or newer. No version file exists, so the target version is unknown.
  • An Anthropic API key (or an OpenAI-compatible endpoint, see section 30).
  • A Databricks workspace with a Genie space, and either a personal access token (dev) or an OAuth app connection (per-user login).

Way 1: like production (one process)

npm run setup     # installs both apps, creates server/.env from .env.example
# edit server/.env: host, Genie space ids, ANTHROPIC_API_KEY, DATABRICKS_TOKEN
npm run build     # builds the UI, then the server
npm start         # then open http://localhost:1976

npm start runs the built server. After any code change, run npm run build again, otherwise old code keeps running. It stops with a message if server/.env or the build is missing.

Way 2: for development (two processes, hot reload)

# terminal 1                    # terminal 2
cd server                        cd ui
npm run dev                      npm run dev
# Mastra on :4111 (+ Studio)     # UI on http://localhost:5173, proxies /bi and /auth to the server

Tests and checks

cd server
npm test                          # unit tests (vitest)
npm run typecheck                 # src/ only
npx tsx scripts/smoke-genie.ts "your question"   # Genie alone, no AI agents
cd ../ui
npm run typecheck                 # npm run build also type-checks

5. Mastra in 5 minutes

Mastra gives you a few building blocks. This app uses exactly these.

Agent

new Agent({
  id: 'suggest_agent',
  instructions: 'You suggest follow-up questions ...',   // the system prompt
  model: model(),                                        // which LLM
  tools: { ... },                                        // what it can call (optional)
})

Think of an agent as a worker with a job description (instructions), a brain (model) and a toolbox (tools).

Tool

createTool({
  id: 'ask-placement',
  description: 'Ask the Databricks Genie space ...',  // the LLM reads this to decide when to use it
  inputSchema: z.object({ question: z.string() }),
  outputSchema: z.object({ summary: z.string(), ... }),
  execute: async ({ question }, { requestContext }) => { ...real code... },
})

A tool is a normal function plus a label. The description and inputSchema are how the LLM learns what the tool does. execute is the real code that runs.

Supervisor pattern

new Agent({ ..., agents: { ...genieAgents } })

When you give an agent an agents list, Mastra lets it call each sub-agent like a tool. Each sub-agent's description tells the supervisor when to use it.

Memory

The supervisor has Memory backed by a small file database (LibSQL, file bi-memory.db). Each chat has a thread id. This is how a follow-up like "and for last year?" works.

Mastra instance and routes

new Mastra({ agents, storage, server }) is the root object. We add our own web routes with registerApiRoute. Mastra runs the web server.

RequestContext

A small bag of values that travels with one request, so tools deep inside sub-agents can read things like the thread id, the session id and the collector.

6. contracts.ts: the shared data shapes

server/src/contracts.ts

This file describes the shapes of data that move between parts of the app. Reading it first teaches you the vocabulary of the system.

GenieResult: what one Genie call returns

export const GenieResultSchema = z.object({
  spaceId: z.string(),
  question: z.string(),
  summary: z.string(),                     // Genie's text answer
  sql: z.string().nullable(),
  columns: z.array(z.string()),
  rows: z.array(z.array(z.unknown())),     // capped (GENIE_ROW_CAP, default 200)
  totalRows: z.number(),
  thinking: z.array(z.string()),           // Genie's reasoning steps
  suggestedQuestions: z.array(z.string()), // Genie's recommended follow-ups
  statementId: z.string().nullable(),      // used to load the full result (Agent mode)
  conversationId: z.string(),
  messageId: z.string(),
  error: z.string().nullable(),
});
export type GenieResult = z.infer<typeof GenieResultSchema>;
  • z.object({...}) declares an object with named fields. .nullable() means "this, or nothing".
  • rows is a list of rows, each a list of values: [["APAC","492.2"],["EMEA","310.7"]]. columns holds the names in the same order.
  • conversationId and messageId are Genie's own ids, needed for follow-ups and for the Helpful / Not helpful buttons.
  • The last line turns the schema into a TypeScript type, so one definition gives both the check and the type.

ChartSpec: a chart, described without a library

export const ChartSpecSchema = z.object({
  type: z.enum(['bar', 'line', 'scatter']),
  title: z.string(),
  x: z.string(),                                    // field names, keys of each data row
  y: z.string(),
  color: z.string().optional(),                     // series field
  xType: z.enum(['category', 'time', 'number']),    // time: ISO date strings, sorted ascending
  data: z.array(z.record(z.string(), z.unknown())), // y (and x for scatter) are numbers
});

This is deliberately neutral. The server does not know which chart library the browser uses (section 26).

FinalAnswer: what the UI finally receives

export const FinalAnswerSchema = z.object({
  answer: z.string(),
  columns: z.array(z.string()),
  rows: z.array(z.array(z.unknown())),
  totalRows: z.number(),                  // rows.length < totalRows => the UI shows a preview
  chartSpec: ChartSpecSchema.nullable(),  // null => UI shows table only
  sources: z.array(z.object({ spaceId, spaceName, question, sql, messageId, conversationId })),
  suggestedQuestions: z.array(z.string()),
});

The final package: the written answer, the table, an optional chart, a list of sources (which Genie question was asked and what SQL ran), and suggested follow-ups.

ChatEvent: the live messages

export type ChatEvent =
  | { type: 'step'; step: 'genie'; status: 'start' | 'done'; detail?: string }
  | { type: 'thinking'; text: string }   // one line of Genie's progress or reasoning
  | { type: 'text'; delta: string }
  | { type: 'final'; result: FinalAnswer }
  | { type: 'suggestions'; questions: string[] }  // sent after final
  | { type: 'error'; message: string };
typemeaningUI reaction
stepA Genie tool started or finishedshows "Querying Genie..."
thinkingOne line of Genie's progressadds a line to the "Genie is thinking" panel
textA few more words of the answerappends them (typing effect)
finalEverything is done, here is the datashows chart, table, SQL
suggestionsFollow-up ideas, a moment latershows follow-up buttons
errorSomething brokeshows the message

Interfaces: promises about behaviour

export interface GenieClient {
  ask(args: {...}): Promise<GenieResult>;
  feedback(args: ...): Promise<void>;
  fetchFullResult?(args: { statementId: string; cap: number; sessionId?: string }): Promise<...>;
}
export interface TokenProvider { getToken(ctx?: { sessionId?: string }): Promise<string> }
export type GenieSpace = { key: string; name: string; description: string; spaceId: string };

An interface says "anything with these functions will do". That is why the app can swap "shared token" for "per-user token", or the Conversation client for the Agent-mode client, without changing the code that uses them. It also makes tests easy: tests pass in a fake. fetchFullResult is optional because only Agent mode has it.

Keep two files in step

ui/src/types.ts is a hand-kept copy of these shapes. Nothing checks that they match. If you change contracts.ts, change types.ts too.

8. conversations.ts: remembering Genie's thread

server/src/genie/conversations.ts 
const store = new Map<string, string>();
const k = (threadId: string, spaceId: string) => `${threadId}::${spaceId}`;
export const getConversationId = (threadId, spaceId) => store.get(k(threadId, spaceId));
export const setConversationId = (threadId, spaceId, conversationId) => void store.set(k(threadId, spaceId), conversationId);

// Latest result per (thread, space), so a later turn can load the full result of a query that was only previewed.
const lastResults = new Map<string, GenieResult>();

Genie keeps its own conversation so follow-ups make sense. We must send the same Genie conversationId on the next question in the same chat. This tiny file is the notebook that remembers it, plus the last result per chat and space (for loading the full result later).

  • A Map is a lookup table: key in, value out. The key joins the chat thread and the space.
  • It lives in memory. After a restart Genie starts a fresh conversation, while the supervisor's own memory (on disk) still remembers the chat.

9. genie/client.ts: talking to Genie (default mode)

server/src/genie/client.ts

This file talks to the Genie Conversation API. It is a normal class with no AI in it. It is used unless GENIE_MODE=agent.

Settings at the top

const ROW_CAP = Number(process.env.GENIE_ROW_CAP ?? 200);
const TIMEOUT_MS = Number(process.env.GENIE_TIMEOUT_MS ?? 180_000);

At most 200 rows are kept (to protect the browser and the AI), and we give up after 3 minutes. Both are changeable in .env.

The constructor

constructor(
  private readonly tokens: TokenProvider,
  host = process.env.DATABRICKS_SERVER_HOSTNAME,
  private readonly fetchFn: typeof fetch = fetch,
  private readonly pollDelaysMs = [1000, 1500, 2000, 3000, 5000],
) { if (!host) throw new Error('DATABRICKS_SERVER_HOSTNAME is not set'); ... }
  • tokens: where to get the login token (works with either login mode).
  • fetchFn: the function that does web requests. Tests pass a fake, so no real network is needed.
  • pollDelaysMs: waits between "are you done yet?" checks: 1s, 1.5s, 2s, 3s, then 5s.

call(): one authenticated web request

const res = await this.fetchFn(`${this.base}${path}`, {
  method,
  headers: { Authorization: `Bearer ${await this.tokens.getToken({ sessionId })}`, 'Content-Type': 'application/json' },
  body: body === undefined ? undefined : JSON.stringify(body),
});
if (!res.ok) throw new Error(`Genie ${method} ${path} failed: ${res.status} ...`);

Every request carries Authorization: Bearer <token>. With OAuth, sessionId picks your token, so Genie runs as you.

ask(): the main function

1

Start. With a conversation id, post the question into it. Without one, call start-conversation. Either way you get a conversation_id and a message_id.

2

Poll. Ask for the message's status until it is COMPLETED. Each status change (for example "Running the query...") and each new reasoning step is passed to onProgress, which becomes a live "thinking" line in the browser. FAILED, CANCELLED, QUERY_RESULT_EXPIRED or 3 minutes of waiting returns an error result.

3

Read attachments. A text attachment is Genie's written answer. A query attachment holds the SQL and its reasoning. Attachments may also carry suggested questions.

4

Fetch the rows from the query's query-result endpoint. Keep the first 200 rows but remember the real total.

5

Return a GenieResult. statementId is always null in this mode.

ask() never throws

Everything sits in a try/catch. On any failure you get a normal GenieResult with error filled in, so the AI agent can explain the error in words instead of the request crashing.

Gotcha

Genie can return numbers as text ("492.2"). Later code converts them where it matters (charts, table alignment).

feedback()

Sends your Helpful / Not helpful rating (POSITIVE or NEGATIVE) to Genie so the space's owners can see how it performs.

10. genie/agentClient.ts: Genie Agent mode (Beta)

server/src/genie/agentClient.ts

Used when GENIE_MODE=agent. It calls POST /api/2.0/genie/agents/{space}/responses and reads a stream of events. Unlike polling, it shows Genie's actual reasoning, each SQL call and the final text. A comment in the file marks this API as Beta.

How it reads the stream

  • sseData() at the bottom turns the response body into a series of parsed JSON events.
  • response.created gives the conversation and message ids.
  • response.output_item.done hands each finished item to onItem(). response.failed and error set result.error.

onItem(): one stream item

Item typeWhat it does
reasoningAdds the text to thinking and shows it live.
function_callShows "Running query: ...". Keeps the SQL if nothing else supplied it.
function_call_outputRemembers the statementId. If the output holds chart JSON (chartJsonOf), stores it as a one-cell result, the same shape the default client returns for charts.
messageThe part with metadata carries the SQL, columns and preview rows. Other parts are prose, cleaned of Databricks citation links and chart placeholders.

Two things only this client does

  • Re-load cut-off chart JSON. The stream cuts long query output at about 600 characters, so a chart's JSON often arrives incomplete. If the SQL mentions chart_json and no table arrived, ask() loads the one-cell result by statement id.
  • fetchFullResult(). Pages through the SQL Statement API until cap rows. This is what lets a user say "show me all the rows" (section 12). It throws "Result is too large to load inline" if the result is stored as external links.

Feedback still goes through the Conversation client (this.chat.feedback).

11. collector.ts: a side channel for data

server/src/mastra/collector.ts 
export type Collector = { results: GenieResult[]; chart: ChartSpec | null; emit?: (e: ChatEvent) => void };
export const newCollector = (): Collector => ({ results: [], chart: null });

export const getCollector = (rc) => {
  const c = rc?.get('collector') as Collector | undefined;
  if (!c) throw new Error('collector missing from request context');
  return c;
};
export const getThreadId = (rc) => (rc?.get('threadId') as string) ?? 'default';

The problem it solves

The AI only handles text. But the browser needs real rows, real SQL and a real chart. Pushing 200 rows through the AI would be slow, costly, and the AI might alter them.

The solution

For each question the server creates an empty collector (a box). Tools drop the full data into it as they run. When the AI finishes, the server opens the box and sends the contents to the browser. The AI sees only a short summary.

 Genie tool  --full rows, SQL, chart-->  [ collector box ]  --> server reads it at the end --> browser
     |
     +--short summary only-->  the AI

 Genie tool  --collector.emit(thinking line)-->  straight to the browser, live

The box is passed inside RequestContext, and it is the same box (a reference), so a change made deep in a sub-agent's tool is visible to the route that created it. emit pushes live events to the browser from inside a tool.

12. askGenie.ts: the two Genie tools

server/src/mastra/tools/askGenie.ts

Both are factories: functions that build a tool. Calling each once per space gives each Genie agent its own pair.

ask-<key>: ask a data question

const result = await client.ask({
  spaceId: space.spaceId,
  question,
  conversationId: getConversationId(threadId, space.spaceId),
  sessionId: requestContext?.get('sessionId') as string | undefined,
  onProgress: (text) => collector.emit?.({ type: 'thinking', text }),
});
if (result.conversationId) setConversationId(threadId, space.spaceId, result.conversationId);
const fromJson = parseGenieChartJson(result.columns, result.rows);
collector.chart = fromJson?.chart ?? null;
  1. Find which chat this is, and call Genie, reusing the earlier conversation id and the user's session id.
  2. Send each progress line to the browser as a thinking event.
  3. Remember the conversation id for follow-ups.
  4. If the result is chart JSON, swap in the real table and set collector.chart (section 13). If not, collector.chart becomes null: the chart always belongs to the latest result, so a later non-chart answer clears an earlier chart.
  5. A one-cell result that is not recognised chart JSON is logged as a warning, to help diagnose.
  6. Save the full result in the collector, and as the "last result" for this chat.
  7. Return a trimmed object to the AI: summary, SQL, columns, only 20 sample rows, totalRows, shownRows, truncated, chartReady, error.

fetch-full-<key>: load every row

The table normally shows a preview (200 rows). When the user asks for everything, this tool loads the previous query's complete result through client.fetchFullResult, up to GENIE_FULL_ROW_CAP (default 5000). It works only in Agent mode, because it needs a statementId. In the default mode it answers "The full result is not available for the previous query." The supervisor is told to ask the user first and never load more on its own.

13. chartSpec.ts: Genie's chart JSON to a chart

server/src/mastra/chartSpec.ts

Charts are built in code, never by an AI. When a user asks for a chart, the supervisor passes the word "chart" to Genie. Genie then returns a single chart_json cell: {type, title, x, y, series, data:[{...}]}.

parseGenieChartJson(columns, rows)

  1. Check the shape: one column, one row, a string that parses as JSON with a data array and string x and y. If not, return null (it is not chart data).
  2. Check that x and y are real columns. Build the real table from data.
  3. Map the type: column or bar becomes bar; line and scatter stay. Anything else, or a non-numeric y, gives no chart (table only) and a warning in the log.
  4. If a series field exists, it becomes the chart's color.

buildChartSpec(...)

const xType = type === 'scatter' ? 'number'
  : type === 'line' && rows.every((row) => isDate(row[xi])) ? 'time' : 'category';
  • xType is number for scatter, time for a line whose x values all look like dates (2024-03 or 2024-03-14), and category otherwise. A bar with dates is treated as categories.
  • Numbers sent as text are converted to real numbers (the y column, and x for scatter).
  • For time, the rows are sorted by date so a line does not zigzag.

Tests: chartSpec.test.ts covers a coloured bar, line and scatter mapping, dated lines, an unsupported type and non-chart input.

14. agents/index.ts: the agents

server/src/mastra/agents/index.ts

The heart of the Mastra part. One function, createAgents(client), builds all the agents. There is no chart agent: charts are plain code (section 13).

Which AI model

const model = () => {
  const baseUrl = process.env.LLM_BASE_URL;
  if (baseUrl) return { id: `litellm/${process.env.LLM_MODEL ?? 'gpt-5.1'}`, url: baseUrl, apiKey: process.env.LLM_API_KEY };
  return `anthropic/${process.env.ANTHROPIC_MODEL ?? 'claude-sonnet-5-5'}`;
};

Two modes: a custom OpenAI-compatible endpoint (for example a proxy) when LLM_BASE_URL is set, or Anthropic by default. The Anthropic key is read from ANTHROPIC_API_KEY by the AI layer (not by this repo's own code).

Agent 1: the Genie agents (one per space)

  • Id genie_<key>. Exactly two tools: ask-<key> and fetch-full-<key>.
  • Its instructions: pass a clear, self-contained question; never invent numbers; report key figures and one caveat; state an error plainly; if the result is truncated, state totalRows and shownRows; use the full-result tool only when asked to; for a chart request put the request in the question and report chartReady; never describe how a chart looks.

Agent 2: the supervisor (bi_supervisor)

const supervisor = new Agent({
  id: 'bi_supervisor',
  instructions: `...`,
  model: model(),
  agents: { ...genieAgents },
  memory: new Memory({ storage: new LibSQLStore({ id: 'bi-memory', url: 'file:./bi-memory.db' }) }),
  defaultOptions: { maxSteps: 12 },
});
  • agents is what makes it a supervisor. memory keeps chat history in bi-memory.db.
  • maxSteps: 12 is a safety limit so one question cannot loop forever.

Its instructions, in plain words

  1. Routing. Placement, status, layer, total limit and FOT premium go to genie_placement. Reinsurer, capacity, authorized or signed, declines to quote and quoted premium go to genie_capacity. If both are needed, ask both. If unclear, ask the user one short question.
  2. Never invent numbers. "Year" means underwriting year. Statuses are in workflow order (Request Quote, Provide Quote, FOT, Authorization, Signed). Trends go years ascending, rankings by value descending. Money in tables and answers is USD millions with one decimal.
  3. Charts come from Genie. When a chart, or a clearly useful ranking, comparison or trend, is wanted, ask Genie for the data as a chart in the same question, using the word "chart". Only bar or column, line and scatter are drawn; for pie, sankey and so on, say it is not supported yet. If chartReady is false, say in one sentence that no chart was available and the table is shown.
  4. Answer style. Short plain prose, no markdown tables or lists. Lead with the insight. Never repeat what the UI already shows. Never mention agents or tools.
  5. Truncation. If the table is only a preview, say so and ask before loading the rest.
  6. Small talk gets a direct answer.

Agent 3: the follow-up agent (suggest_agent)

Writes up to three short, self-contained follow-up questions (under 90 characters, answerable from the data described). Used by suggest.ts.

Prompts are code

These instruction strings are the easiest place to change behaviour, and nothing tests them. Small wording changes can change behaviour. After any edit, try real questions end to end.

16. mastra/index.ts: the server itself

server/src/mastra/index.ts

This file wires everything together and defines all the web routes. It is the one file to read in full.

Setup at the top

import 'dotenv/config';                 // loads .env into process.env
const oauth = oauthEnabled();           // is DATABRICKS_CLIENT_ID set?

Top to bottom: pick the login mode, create a token provider that picks the right way to get tokens, create the Genie client (Agent mode or default), then create the agents with it.

authenticate(): who is calling?

async function authenticate(c: any) {
  if (!oauth) return { user: 'dev' };
  const sessionId = readSessionId(c.req.header('cookie'));
  const session = getSession(sessionId);
  if (!sessionId || !session) return c.json({ error: 'Please log in.', relogin: true }, 401);
  try { await tokens.getToken({ sessionId }); }          // refreshes if needed
  catch (e) { if (e instanceof AuthError) return c.json({ error: e.message, relogin: true }, 401); throw e; }
  return { sessionId, user: session.user };
}

It returns either the caller or a ready-made 401 response. Routes check who instanceof Response and return it. In shared-token mode everyone is the user dev. This is the app's guard.

The chat route: POST /bi/chat

1

Authenticate. Check threadId and message exist (400 if not). Prefix the thread id with the user name, so threads are per user.

2

Create a fresh collector and a RequestContext holding the collector, thread id and session id. Set collector.emit so tools can stream progress.

3

Open a ReadableStream and call supervisor.stream(message, ...) with memory scoped to the thread and the request's abort signal.

4

Loop over the stream. text-delta becomes a text event. tool-call and tool-result for a tool whose name contains "genie" become step events. An error chunk throws.

5

Build the FinalAnswer from the collector: the latest result that has columns, the chart spec, one source per Genie message, and Genie's own follow-ups. Send it as a final event.

6

If Genie gave no follow-ups and at least one result had no error, ask suggestFollowUps and send a suggestions event.

7

Any exception is sent as an error event. finally closes the stream.

const sse = (e: ChatEvent) => `data: ${JSON.stringify(e)}\n\n`;   // one SSE message

The response headers are Content-Type: text/event-stream and Cache-Control: no-cache.

The feedback route: POST /bi/feedback

Authenticates, rejects an unknown spaceId (400), and forwards the rating to Genie. A Genie failure returns 502 with the message.

The auth routes

RouteWhat it does

serveUi: hosting the web page

Middleware on /*. When UI_DIST is set, it serves the built UI files from that folder. It skips non-GET requests and paths starting with /api, /bi, /auth/ or /swagger, blocks paths that climb out with .., and falls back to index.html so reloading any path works. This is why new routes should live under /bi/ or /auth/.

The Mastra instance

export const mastra = new Mastra({
  agents: { supervisor, suggestAgent, ...genieAgents },
  storage: new LibSQLStore({ id: 'mastra-storage', url: 'file:./mastra.db' }),
  server: {

CORS (the browser rule about which addresses may call the server) allows only the dev UI address. In production the UI comes from the same address, so it is not needed.

Error handling to know about

Request bodies are barely checked. threadId and message are checked for presence; the feedback rating is not checked; invalid JSON is not handled in the route code. The zod schemas in contracts.ts are not applied to requests. Errors inside the stream return HTTP 200 (the response has already started) and are sent as an error event, but are not written to the server log.

There are two modes, chosen once at start by one setting:

Access control

The app has no roles or permissions of its own. What a user sees depends on their Databricks account, because Genie runs with their token and Unity Catalog permissions apply. The only separation the app adds is per-user chat threads. In shared-token mode all users are dev and share threads.

19. oauth.ts: the login steps

server/src/auth/oauth.ts

Configuration

export const oauthConfig = () => ({
  host: `https://${(process.env.DATABRICKS_SERVER_HOSTNAME ?? '')...}`,
  clientId: process.env.DATABRICKS_CLIENT_ID ?? '',
  redirectUri: process.env.DATABRICKS_REDIRECT_URI ?? `http://localhost:${port}/auth/callback`,
  scopes: 'all-apis offline_access',
});
export const oauthEnabled = () => Boolean(process.env.DATABRICKS_CLIENT_ID);

The scope offline_access is what gives a refresh token. The redirect address must match exactly what is registered in the Databricks account console.

The pending list

A redirect to Databricks and back is a new request, so the PKCE verifier is kept in a Map keyed by state. Entries expire after 10 minutes and are deleted when used once.

challengeOf() and buildLoginUrl()

challengeOf is the SHA-256 hash of the verifier (the "fingerprint"). buildLoginUrl makes a random state and verifier, stores them, and returns the Databricks authorize URL with code_challenge and code_challenge_method=S256.

exchangeCode(), refreshTokens(), tokenRequest()

  • exchangeCode(code, state) looks up and removes the pending entry (error if unknown or older than 10 minutes), then asks the token endpoint to swap the code plus verifier for tokens.
  • refreshTokens(refreshToken) asks for a new access token.
  • tokenRequest is the shared helper. It returns { accessToken, refreshToken, expiresAt } and throws on HTTP errors.

fetchUserName()

Reads the user's name from the SCIM Me endpoint. The name is optional, so any failure falls back to 'user'.

20. sessions.ts: logged-in users

server/src/auth/sessions.ts

Storing sessions

const sessions = new Map<string, Session>();     // in server memory
export const createSession = (tokens, user) => { const id = randomBytes(32).toString('base64url'); sessions.set(id, { ...tokens, user }); return id; };

A session holds the access token, refresh token, expiry time and user name. It lives in memory, so a server restart signs everyone out, and two server copies would not share sessions.

The cookie

`${COOKIE}=${value}; HttpOnly; SameSite=Lax; Path=/; Max-Age=${maxAgeSec}${secure ? '; Secure' : ''}`

The cookie is named bi_sid and lasts 8 hours. HttpOnly hides it from page scripts. Secure is added only when the request URL is https.

SessionTokenProvider.getToken(): always hand out a valid token

  • Returns the access token if it is valid for more than 60 seconds.
  • Otherwise refreshes it with the refresh token. If several calls notice expiry at once, it refreshes once and shares the result.
  • If there is no refresh token or the refresh fails, it deletes the session and throws AuthError, which the chat route turns into a 401 with relogin: true.

FallbackTokenProvider

One line of logic: in OAuth mode use the session provider, otherwise use the shared token provider.

Tests in auth.test.ts cover the PKCE challenge, the authorize URL, single-use state, errors, cookie parsing, refresh, shared refresh for concurrent calls, and ending a session when refresh fails. The README notes the real Databricks login has only been tested with a placeholder client id.

streamChat(): reading the live stream

const res = await fetch('/bi/chat', { method: 'POST', headers: {...}, body: JSON.stringify({ threadId, message }), signal });
if (res.status === 401) throw new ReloginError(...);
const reader = res.body.pipeThrough(new TextDecoderStream()).getReader();
let buf = '';
for (;;) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += value;
  let i: number;
  while ((i = buf.indexOf('\n\n')) >= 0) {
    const frame = buf.slice(0, i); buf = buf.slice(i + 2);
    const data = frame.split('\n').filter((l) => l.startsWith('data:')).map((l) => l.slice(5).trim()).join('');
    if (data) onEvent(JSON.parse(data) as ChatEvent);
  }
}
  • It uses fetch and a stream reader, not the browser's EventSource, because EventSource cannot send a POST body.
  • The text arrives in arbitrary chunks, so it is collected in buf and split on blank lines. Each complete block is parsed and handed to onEvent.
  • A 401 becomes ReloginError, which sends the user back to the login page.

sendFeedback()

Posts the rating, with the space id, conversation id and message id, to /bi/feedback.

Switching, and shipping just one

  1. To try another library, comment out the active line and uncomment another.
  2. To ship one, delete the other two renderer files first (and plotly.d.ts if you keep Recharts or D3), then uninstall their packages in ui/.
  3. Do not delete packages first: TypeScript checks every file in ui/src, even ones the switch does not import, so all three packages must stay installed until the files are gone.

Rough bundle sizes seen when each was built: Recharts about 643 kB, Plotly about 1,457 kB, D3 about 306 kB. These change with versions.

How each draws

  • Recharts: pivots the rows into one row per x value with a key per series, then uses BarChart, LineChart or ScatterChart. Time axes use a numeric time scale with month-and-year labels.
  • Plotly: builds one trace per series and calls Plotly.react in an effect, with Plotly.purge on cleanup. The axis type is category, date or linear from xType.
  • D3: measures its container with a ResizeObserver, then redraws SVG: band, UTC time or linear x scale, a linear y scale, stacked rectangles for bars, lines and circles, and a legend on the right.

29. How to change things

Add a Genie space

  1. Add an entry to genieSpaces in server/src/genie/registry.ts (key, name, description, spaceId). Use a setting for the id, following the existing pattern, and add it to server/.env.example.
  2. Write the description carefully; the supervisor routes by it.
  3. Also add routing words for it in the ROUTING block of the supervisor instructions in agents/index.ts, which names genie_placement and genie_capacity by hand. The README mentions only the first step.
  4. The agent, its two tools and its registration are created automatically. Rebuild.

Add or change a chart type

  1. Server: map the new type name in parseGenieChartJson (chartSpec.ts) and extend ChartSpecSchema in contracts.ts.
  2. Browser: extend ChartSpec in types.ts and draw it in all three renderers (or just the one you keep).
  3. Update the "only bar or column, line and scatter are drawn" sentence in the supervisor instructions.
  4. Add a test in chartSpec.test.ts.

Add an API route

const pingRoute = registerApiRoute('/bi/ping', {
  method: 'POST',

Add something to the answer screen

  1. If the server must send new data, add it to FinalAnswer in both contracts.ts and types.ts, and fill it in the chat route.
  2. Write a small component in components.tsx and use it inside Details.
  3. Add a few lines to styles.css. Run npm run typecheck and npm run build in ui/.

Change how the assistant answers

Edit the instruction text in agents/index.ts. Several rules exist because the AI once did the opposite. Test with real questions.

Add a setting

Read it with process.env.NAME ?? default, add it to server/.env.example, and list it in section 30.

  • .env.example lists every setting above except UI_DIST and API_URL. Required settings are blank; optional ones are commented out with #. Never leave an optional setting blank: NAME= counts as set and replaces the default (GENIE_ROW_CAP= becomes 0 rows, ANTHROPIC_MODEL= breaks the model name).

31. Build, test, deploy

What the repo does not contain

No Dockerfile, Helm chart, CI or CD workflow, security-scan config or release notes. This section describes the build and tests, which the repo shows, and lists questions for deployment, which it does not.

The build

 npm run build (root)
   |
   +--> ui:     tsc --noEmit   (type check)
   +--> ui:     vite build     (output: ui/dist)
   +--> server: npx mastra build  (output: server/.mastra/output)

Run by run.mjs. If a step fails, it exits and later steps do not run. Both output folders are git-ignored. npm start runs mastra start --env .env in server/ with PORT and UI_DIST set, after checking that .env and both builds exist. It runs the built copy, so rebuild after any change.

Tests

WhereCommandCovers
server/npm testLogin (PKCE, sessions, refresh), both Genie clients, chart building

The Genie client tests pass a fake fetch, so they never call Databricks. Not tested: the routes, the tools, the agents and their instructions, suggest.ts, and everything in ui/.

Questions to answer before shipping

  1. Where is the pipeline, and what does it run?
  2. Are there security or dependency scans?
  3. Which environments exist (dev, QC, prod) and how does code reach each?
  4. How is the app packaged (container, plain Node)?
  5. How are settings and secrets given to each environment?
  6. Is there more than one server copy? Sessions and conversation ids are in memory, so more than one copy would break sign-in.
  7. How is the release done and approved?

Things to check on any server you deploy to

  • The server needs write access to its working folder for mastra.db and bi-memory.db.
  • Browsers load fonts from Google Fonts.
  • The OAuth redirect address must match the registered one.
  • The cookie gets Secure only for https request URLs. Check what a proxy in front forwards.
  • CORS allows only http://localhost:5173. Fine when the UI and API share an address.

33. Gotchas and known limits

Build and run

  1. npm start runs old code until you rebuild. The server runs the built copy in server/.mastra/output. This happened for real: the UI was rebuilt for a new chart format, the server was not, the old server kept sending the old format, and the new chart code crashed on it. Rebuild both parts after any change. The UI now survives a bad chart (ChartBoundary).
  2. The server build can fail with EBUSY on Windows. A still-running server, or a tool watching or syncing the folder, locks server/.mastra/output. Stop the server, delete the folder, build again. Keep the project outside synced folders if you can.
  3. The UI type-checks every file, even unused chart renderers. All three chart packages stay installed until you delete the files you do not want.
  4. The server type check skips scripts/. tsconfig.json includes only src/**/*.ts.

Data

  1. Two copies of the data shapes (contracts.ts and types.ts), kept in step by hand.
  2. The table is a preview. Rows are cut to 200. Loading up to 5000 works only in Agent mode.
  3. Only the latest result is shown. If a question used both spaces, the table shows one. A later non-chart answer clears an earlier chart.
  4. Bars with dates use text categories, not a time axis. Only lines get one.
  5. A bad chart is silent. ChartBoundary hides it and logs to the browser console only.

State

  1. Everything important is in memory: sessions, PKCE state, Genie conversation ids, last results. A restart loses them, and two server copies cannot share them. After a restart the supervisor's memory (on disk) and Genie's conversation (in memory) no longer match.
  2. A page reload shows an empty chat but keeps the thread. The thread id is in localStorage; the messages are only in React state. Follow-ups still continue the old thread on the server.

Agents

  1. Routing rules live in two places (the registry descriptions, and the hand-written ROUTING block). A new space needs both.
  2. Agent behaviour is untested text. Try real questions after any edit.
  3. Charts depend on Genie's wording. The supervisor must use the word "chart". An unknown shape gives a table only.
  4. Agent mode is a Beta API and cuts long query output at about 600 characters, so chart JSON is reloaded by statement id.

Security

  1. Request bodies are barely checked (section 16).
  2. Stream errors return HTTP 200 and are not logged on the server.
  3. The [genie] unparsed single-cell result warning may contain data.
  4. Fallback Genie space ids are hard-coded in registry.ts. Decide whether that belongs in source.
  5. The cookie Secure flag depends on the request URL, which may be http behind a TLS-ending proxy.
  6. CORS is fixed to http://localhost:5173.
  7. Shared-token mode makes every user dev, with shared threads. Dev only.

Setup and docs

  1. A blank setting is not the same as an unset one. NAME= in .env replaces the default instead of using it (section 30).
  2. Fonts come from Google Fonts.
  3. The sidebar uses a text wordmark, not the logo file.
  4. The README still mentions a chart_agent that does not exist. Charts are plain code. Trust the code.
  5. Confirm the Genie spaces are attached to the right data. The README notes early tests returned placement data and read "corridor" as a region.
  6. LLM wording and chart choice can vary between runs. The figures come from Genie.
